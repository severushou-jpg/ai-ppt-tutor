# AI PPT Tutor 项目阶段评估与下一阶段建议

**评估日期：** 2026 年 7 月 15 日  
**评估对象：** `ai-ppt-tutor` 当前代码、仓库材料与已有项目记录  
**评估目的：** 客观判断当前阶段，明确下一阶段“底层算法、Prompt、UI”三条工作线的优先级、任务与验收标准

## 一、执行摘要

### 核心结论

AI PPT Tutor 当前最准确的定位是：**已完成核心闭环的本地技术 MVP / Pre-alpha 功能原型，处于“概念验证完成、公开试点尚未就绪”的阶段。**

它已经超过纯概念或静态 Demo：项目可以在本地运行，接收 PDF/PPTX 文件，提取文字，调用通义千问生成结构化讲解，并支持围绕课件提问和生成练习题。但它尚未具备一个可稳定交给真实用户持续使用的产品所需的质量验证、检索与引用、异常处理、数据与隐私保护、用户体系、监控、测试和反馈闭环。

因此，下一阶段不宜把目标简单表述为“继续优化三个部分”，而应统一为一个可验收目标：

> **在 4–6 周内，把本地功能原型推进为可供 30–50 名学生进行封闭试点的 Pilot-ready MVP，并建立第一套可量化的 AI 回答质量与学习体验评价基线。**

### 当前阶段的客观边界

- **已经证明：** 基础技术链路可行；用户可从课件上传进入 AI 讲解和练习环节；生产构建可以完成。
- **尚未证明：** 回答是否忠于课件、是否比通用聊天工具更有效、是否能处理长课件和多文件、学生是否愿意持续使用、单位用户成本是否可控。
- **最大风险：** 当前系统会把提取文本直接截断到前 25,000 个字符，既没有按页/幻灯片检索，也没有引用来源；当文件较长或问题涉及后半部分时，回答质量不可控。
- **最合理的下一里程碑：** 不是立即扩充大量功能，也不是立即训练模型，而是先建立“可检索、可引用、可评测、可试用”的基础版本。

## 二、评估依据与方法

本评估基于以下可核查证据：

1. 当前 Next.js 项目代码与依赖配置；
2. 前端页面、文件上传和对话逻辑；
3. 后端文件解析、Prompt 组装与通义千问 API 调用逻辑；
4. `AI tutor 进度.docx`、访谈准备材料与项目进展手册；
5. 本地工程验证结果：`npm run build` 通过，`npm run lint` 存在 2 个错误；
6. 当前仓库提交历史和文件结构。

本评估没有真实用户数据、线上运行数据或标准化答案质量测试结果，因此不会推断尚未被证据支持的产品效果。

## 三、当前已完成的能力

### 1. 产品核心闭环已经成立

用户可以完成以下基本流程：

1. 上传 PDF 或 PPTX 课件；
2. 触发基于课件文本的结构化讲解；
3. 继续围绕当前课件进行问答；
4. 一键进入“测验模式”，请求生成练习题；
5. 在对话区阅读 Markdown 格式的 AI 输出。

这说明项目已经完成最小价值假设的技术表达：**静态课件可以被转换为可交互的讲解、问答和练习。**

### 2. 工程骨架可继续迭代

- 使用 Next.js 16、React 19 和 TypeScript 构建前端；
- 使用服务端 API Route 隐藏大模型密钥；
- PDF 与 Office 文件分别接入了解析库；
- 对话保留最近 10 条历史消息；
- 前端具备基本加载态、错误消息、清空记录和自动滚动；
- 生产构建成功，说明当前版本不存在阻断构建的类型或打包错误。

### 3. 项目定位已有初步清晰度

现有材料已经把产品定位为：将大学课件转化为可讲解、可提问、可生成练习的 AI 学习平台，并计划以 UNNC 学生为首批试点对象。这一定位比“通用 AI 聊天”更聚焦，也适合形成早期验证场景。

## 四、当前不足与阶段评分

以下评分采用 5 分制，仅反映“进入真实用户封闭试点”的准备程度，不代表项目长期价值。

| 维度 | 评分 | 客观判断 |
|---|---:|---|
| 问题与目标用户定义 | 3.0/5 | 学生课件学习场景明确，但首批用户、课程与高频任务仍需进一步收窄。 |
| 核心功能原型 | 3.0/5 | 上传、讲解、问答、练习主链路已实现；缺少课程空间、多文件和持久化。 |
| AI/检索可靠性 | 1.5/5 | 当前为全文截断后直接调用模型；无分块、检索、重排、引用和系统化评测。 |
| Prompt 与教学设计 | 2.0/5 | 已有结构化教学要求，但讲解、问答、测验共用一个系统提示，缺少分任务策略与质量约束。 |
| UI/UX 完整度 | 2.0/5 | 桌面端基本对话可用；缺少处理进度、来源定位、课程管理、移动适配和完善反馈。 |
| 工程质量与测试 | 1.5/5 | 构建通过；Lint 有 2 个错误，尚无自动化测试、接口契约测试和错误恢复测试。 |
| 部署与可运维性 | 1.0/5 | 仍以本地运行记录为主；无线上环境、日志指标、限流、成本监控和服务等级基线。 |
| 用户验证与学习效果 | 1.0/5 | 尚无规模化真实用户测试、留存、满意度或学习效果证据。 |
| 隐私、安全与合规 | 1.0/5 | API Key 位于服务端是正确起点，但缺少上传限制、内容保留政策、隐私告知、滥用防护和数据删除机制。 |

### 阶段判断

综合来看，项目处于五阶段模型中的第 2 阶段：

1. 问题/概念；
2. **可运行功能原型（当前）；**
3. 可封闭试点 MVP；
4. 有真实使用与效果证据的产品；
5. 可规模化运营与商业化的产品。

## 五、三条工作线的正确关系

“底层算法、Prompt、UI”并不是三个完全独立的方向。建议按以下依赖关系推进：

1. **先建立评测基线与课件检索链路；**否则无法判断算法或 Prompt 的优化是否真实有效。
2. **在稳定的检索输入上迭代分任务 Prompt；**否则 Prompt 会被迫补偿错误或缺失的上下文。
3. **围绕稳定的用户任务重构 UI；**否则 UI 容易围绕尚未确定的流程反复返工。
4. 三条线最终共同服务于同一组试点指标：正确性、可追溯性、完成率、延迟、成本和学习体验。

## 六、方向一：优化底层算法

### 目标

把目前“整份文本直接塞给模型”的链路升级为：**可处理长文档和多文件、能够检索相关片段、能够显示来源、能够被评测的课件知识系统。**

### P0：试点前必须完成

#### 1. 建立标准化文档摄取管线

- PDF 按页、PPTX 按幻灯片保留结构与顺序；
- 清洗页眉页脚、重复空白和乱码；
- 为每个文本块保存 `document_id`、文件名、页码/幻灯片号、标题层级等元数据；
- 对空文件、扫描件、加密文件、超大文件提供明确错误提示；
- 对图片型课件预留 OCR 路径，但不必在第一周同时支持所有格式。

**验收建议：** 用 10 份不同课程课件测试，成功解析率达到预设目标；抽查页码/幻灯片号与原文对应关系；解析失败能够给出用户可理解的原因。

#### 2. 引入分块、检索与引用

- 先按标题、页/幻灯片边界做语义分块，再设置适度重叠；
- 建立向量检索，并保留一个关键词检索通道；
- 采用混合检索召回候选片段，再根据问题相关性重排；
- 只把最相关的片段送入模型，回答中返回页码/幻灯片引用；
- 当课件中没有依据时，明确回答“材料中未找到”，避免编造。

**验收建议：** 建立至少 50 个带标准来源页的测试问题，记录 `Recall@K`、引用命中率、无依据问题拒答率与人工正确性评分。不要只凭主观感觉调整参数。

#### 3. 建立最小评测集和回归测试

题目应至少覆盖：

- 事实定位题；
- 跨页概念整合题；
- 公式或定义解释题；
- 课件中不存在答案的问题；
- 长课件后半部分的问题；
- 中文提问、英文课件等跨语言场景；
- 练习题生成及答案依据检查。

每次更换模型、分块、检索或 Prompt 后，必须在同一评测集上对比，而不是只展示几个成功案例。

#### 4. 增加必要的服务保护

- 限制文件类型、大小、页数与请求频率；
- 校验 `history` JSON 和模型返回结构；
- 给解析和大模型请求设置超时、重试与可理解的错误码；
- 记录延迟、Token、估算成本、成功率和错误类型，但避免记录不必要的课件原文；
- 明确临时文件和文本的保留/删除策略。

### P1：完成 P0 后推进

- 建立“课程空间”，支持同一门课的多份课件检索；
- 对已上传文档做内容哈希和解析缓存，减少重复成本；
- 引入对话摘要或结构化学习状态，替代简单截取最近 10 条消息；
- 支持用户选择讲解深度、语言、先修水平和考试目标；
- 对公式、表格和图片建立专门解析策略；
- 建立模型路由：简单任务使用低成本模型，复杂推理使用更强模型。

### P2：有试点数据后再考虑

- 个性化知识掌握模型、错题本和间隔复习；
- 基于学生回答的难度自适应；
- 微调或蒸馏小模型；
- 本地/校内模型部署。

**重要判断：** 当前阶段不建议优先做模型微调。项目最明显的质量瓶颈是上下文摄取、检索、引用和评测，而不是缺少一个专门训练的新模型。

## 七、方向二：优化 Prompt 提示词

### 目标

把一个通用系统提示拆分成**可版本化、可测试、按教学任务专门设计的 Prompt 系统**。

### 1. 按任务拆分 Prompt

至少拆为四类：

1. **课件导学：** 给出章节目标、先修知识、知识结构和建议学习顺序；
2. **基于材料问答：** 只依据检索片段回答，附来源，证据不足时拒答；
3. **概念讲解：** 根据用户水平控制深度，提供例子、易错点和检查理解的问题；
4. **练习生成与批改：** 控制题型、难度、知识点覆盖，生成答案、解析、评分标准和来源。

### 2. 使用结构化输入，而不是拼接大段文本

Prompt 输入应明确区分：

- 系统角色和不可违反的规则；
- 用户画像/学习目标；
- 检索到的课件片段及其来源；
- 当前任务类型；
- 对话摘要；
- 输出格式要求。

这样可以降低模型把课件内容、用户指令和系统规则混在一起的风险。

### 3. 为“忠于课件”设置硬约束

- 每个核心结论必须能对应到来源片段；
- 不把模型常识伪装成课件内容；
- 如补充课外知识，明确标注“补充说明”；
- 课件信息不足时主动指出缺口；
- 防止上传文档中的文本覆盖系统指令，降低 Prompt Injection 风险。

### 4. 改进教学法设计

- 先诊断：询问课程、学习目标、已有基础和考试时间；
- 再讲解：使用“概念—例子—反例—易错点—自检”的结构；
- 再练习：从回忆、理解、应用逐步增加难度；
- 再反馈：针对学生答案解释错误原因，而不是只给正确答案；
- 最后复盘：生成本次掌握点、薄弱点和下一步建议。

### 5. Prompt 版本管理与 A/B 评价

每个 Prompt 应有版本号、变更说明和适用任务。评价至少包括：

- 事实正确性；
- 引用正确性；
- 课件覆盖度；
- 教学清晰度；
- 难度匹配；
- 冗长度；
- 格式稳定性；
- 单次成本和延迟。

第一轮可以由 2–3 名人工评审对固定样本盲评；进入试点后，再结合学生“有帮助/没帮助”、引用点击和追问率。

### 6. 建议的输出结构

不要让所有回答都强制使用同一套长模板。建议根据任务动态选择：

- 简短事实问答：结论 + 依据 + 来源；
- 概念讲解：学习目标 + 解释 + 例子 + 易错点 + 自检；
- 练习：题目 + 难度/知识点 + 可折叠答案 + 解析 + 来源；
- 章节复习：知识地图 + 高频重点 + 薄弱点 + 复习计划。

## 八、方向三：优化 UI 界面

### 目标

把当前“文件上传 + 聊天窗口”升级为**围绕课件学习任务组织的工作区**，并让用户始终知道系统在做什么、依据是什么、下一步可以做什么。

### P0：试点前必须完成

#### 1. 重构首屏与学习流程

建议流程：

1. 创建课程/学习会话；
2. 上传课件并显示解析进度；
3. 解析完成后展示文件、页数、识别状态；
4. 让用户选择“快速导学 / 深入讲解 / 问答 / 生成练习”；
5. 进入学习工作区。

这比上传后立即进入通用聊天更能体现产品差异。

#### 2. 建立三栏或可折叠工作区

- 左侧：课程、文件与学习会话；
- 中间：对话/讲解/练习主区域；
- 右侧：课件原页、引用片段和知识点目录；
- 小屏幕改为抽屉或标签页，避免固定 320px 侧栏挤压内容。

#### 3. 完善系统状态

必须覆盖：上传中、解析中、索引中、生成中、完成、失败、可重试、文件不支持、文件过大、网络超时、额度不足等状态。进度文案应描述真实阶段，而不仅是一个旋转图标。

#### 4. 让引用可见、可点击

回答中的来源应能跳转到对应页/幻灯片，并高亮相关片段。这是建立信任和区别于通用聊天工具的关键 UI，而不是装饰性功能。

#### 5. 修复基础可用性问题

- 输入框支持多行、`Enter` 与 `Shift+Enter` 的明确行为；
- 生成时禁用重复提交，但允许停止生成；
- 上传后允许查看、更换和删除文件；
- 清空记录前二次确认；
- 提供空状态示例问题；
- 修复 ESLint 错误并补齐键盘操作、焦点、标签和颜色对比；
- 更新页面标题、描述、语言属性和品牌信息。

### P1：提高学习体验

- 讲解、问答、练习使用不同的内容卡片，而不都显示为聊天气泡；
- 答案和解析默认折叠，支持逐题作答；
- 提供“太难 / 太简单 / 换个例子 / 只讲这一页”等快捷控制；
- 用户可对回答标记“有帮助”“不准确”“引用错误”；
- 自动生成本次学习摘要与下一步；
- 保存最近课程与会话，支持继续学习；
- 加入简洁隐私提示：文件用途、保留时间、删除方式。

### P2：有数据后优化

- 知识点掌握度视图；
- 错题与间隔复习；
- 教师端内容配置和班级分析；
- 更完整的品牌视觉与动效。

## 九、建议的 4–6 周执行路线图

| 阶段 | 重点任务 | 交付物 | 退出条件 |
|---|---|---|---|
| 第 1 周：基线 | 修复 Lint；建立 10 份课件和 50 个问题的评测集；定义日志、隐私和上传限制 | 评测集 v1、指标表、错误清单 | 当前版本有可重复的质量基线 |
| 第 2–3 周：算法 | 分页/分幻灯片解析、分块、混合检索、重排、引用、拒答 | RAG 链路 v1、引用 API、回归结果 | 长文档后半部分问题可检索；回答可追溯 |
| 第 3–4 周：Prompt | 拆分导学/问答/讲解/练习 Prompt；结构化输出；版本化 A/B 测试 | Prompt v1 套件、盲评结果 | 固定评测集上质量稳定且格式可控 |
| 第 4–5 周：UI | 上传流程、状态、学习模式、引用面板、移动适配、反馈入口 | Pilot UI、关键流程测试 | 新用户无需指导可完成上传到练习 |
| 第 5–6 周：试点 | 部署封闭测试；招募学生；监控成本、错误与体验；修复 P0 问题 | 试点报告、问题优先级、下一版本计划 | 有真实使用数据和继续/停止的决策依据 |

## 十、建议的试点指标

以下是建议的“目标与决策阈值”，不是当前已实现结果。应在试点前根据课程难度和成本预算最终确认。

### AI 与检索质量

- 解析成功率；
- 标准问题 `Recall@K`；
- 引用命中率与引用页准确率；
- 有依据回答的人工正确率；
- 无依据问题的正确拒答率；
- 练习题答案与课件的一致性。

### 产品体验

- 从上传到首次有效回答的完成率；
- 首次有效回答所需时间；
- 关键错误率与重试成功率；
- 回答“有帮助”比例；
- 引用点击率；
- 7 日内再次使用比例；
- 用户愿意继续使用/推荐的比例。

### 学习效果

- 使用前后短测分数变化；
- 自评理解度变化；
- 完成同一学习任务的时间；

## 十二、最终建议

项目当前最有价值的成果，是已经用很小的工程规模跑通了“课件进入—AI 教学输出”的核心闭环。下一步的关键不是继续增加看起来丰富的功能，而是把这个闭环变得**可靠、可追溯、可评测、可交给真实学生使用**。

三条工作线的推荐投入顺序为：

1. **底层算法与评测：45%**——解决长文档、检索、引用和质量可测问题；
2. **Prompt 与教学设计：30%**——把不同学习任务做深，形成真正的教学体验；
3. **UI 与试点体验：25%**——让用户顺利完成任务并产生可用反馈数据。

当项目完成封闭试点，并能展示“回答更可信、学习更高效、学生愿意复用”的数据后，它才会从技术 MVP 进入有真实产品证据的阶段。届时再讨论模型微调、更多格式、教师端、商业模式和规模化部署，会更稳健，也更容易获得学校孵化、基金或导师支持。
